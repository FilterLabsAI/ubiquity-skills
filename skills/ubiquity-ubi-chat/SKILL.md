# Ubiquity: Ubi chat (feed Q&A assistant)

Covers chatting with "Ubi", the assistant that analyzes a pipeline's feed
artifacts and answers questions about them (distinct from the discovery-time
Ubi chat bubble covered in `ubiquity-pipeline-creation`, which only parses
the initial search query -- this is the standing per-feed chat on the
Understand tab, gated behind "Enable Ubi", see `ubiquity-understand-layer`).
Requires a valid Bearer token -- see `ubiquity-auth`.

## Listing chat sessions -- CONFIRMED on the wire
```
GET /api/understand/chat/sessions?keycloak_user_id=<url-encoded email>&limit=50&offset=0&feed_id=<feed_id>
```
Returns `[]` when none exist yet, otherwise an array of session objects:
```json
{
  "id": "<session_uuid>", "keycloak_user_id": "<email>", "feed_id": 1663,
  "title": "<auto-generated from the first user message, truncated to ~50 chars + ...>",
  "filter_state": {
    "topics": null, "entities": null,
    "dateRange": {"start": "2026-09-02", "end": "2026-10-04"},
    "siteTypes": ["micro_blog"],   // auto-derived from the question text, see below
    "metricName": null, "textSearch": null, "entityTypes": null
  },
  "total_input_tokens": 0, "total_output_tokens": 0,   // observed 0 even after a real exchange -- not populated live
  "inherit_permissions": true,
  "created_at": "...", "updated_at": "..."
}
```
Sessions are scoped per `(user, feed)` pair -- a given feed can have
multiple chat threads per user, like separate conversations. **Each
session auto-derives a `filter_state` from its first message's wording**:
asking "How many **Twitter** sources..." produced
`siteTypes: ["micro_blog"]` automatically (no explicit filter UI needed to
scope by platform-type) -- Ubi's session-creation step evidently parses the
first message for implicit scoping hints (platform/source-type, maybe date
range, topic) the same way the discovery-time query parser does. Don't
assume the chat only answers from the whole-feed default scope unless the
first message was topic/platform-neutral.

## Starting a new chat / sending a message -- CONFIRMED on the wire
The UI's **"New Chat" button is purely a client-side state reset -- it
fires NO network call.** It just clears the active conversation to the
empty state (shown with three canned starter prompts):
- "Summarize the recent artifacts from my feed, highlighting key themes and
  important findings."
- "List the main themes and topics that appear in the recent artifacts."
- "Analyze and evaluate the overall tone and sentiment of the recent
  artifacts."

A session is only created **lazily, server-side, on the first actual
message**. Confirmed sequence when you type a message and hit send:
```
POST /api/understand/chat/sessions                 # creates the session (feed_id, derived filter_state, title)
POST /api/understand/chat/sessions/<new_session_id>/messages   # sends your message, gets Ubi's reply
```
The new session then shows up in a subsequent
`GET /api/understand/chat/sessions?...` list call (confirmed: appeared with
auto-derived `filter_state.siteTypes` and a truncated `title` immediately
after sending).

**Driving this with `browser_exec`:** the textarea
(`placeholder="Ask follow-up questions or request new analysis..."` once a
session has started, or the same input in the empty state) is a
React-controlled input -- plain `fill_input` keystroke simulation can hang/
timeout on it under load (observed: `Input.dispatchKeyEvent` timing out
mid-type and leaving the tab on `about:blank`, requiring a full SPA
re-bootstrap per `ubiquity-auth`'s localStorage trick). **Prefer setting
`.value` via the native setter + dispatching an `input` event**, which
React picks up reliably without the keystroke round-trip:
```js
const ta = document.querySelector('textarea[placeholder="Ask follow-up questions or request new analysis..."]');
const setter = Object.getOwnPropertyDescriptor(window.HTMLTextAreaElement.prototype, 'value').set;
setter.call(ta, "your question text");
ta.dispatchEvent(new Event('input', { bubbles: true }));
// then click the single (icon-only, unlabeled) <button> in the same form/container as the textarea
```

## Reading messages / replaying history -- CONFIRMED on the wire
```
GET /api/understand/chat/sessions/<session_id>/messages?keycloak_user_id=<email>&limit=100&offset=0
```
Returns an array of message objects in chronological order:
```json
{
  "id": "<message_uuid>", "session_id": "<session_uuid>",
  "role": "user" | "assistant",
  "content": "<markdown text -- assistant replies use headers, tables, emoji, blockquoted citations>",
  "input_tokens": null, "output_tokens": null, "reasoning_tokens": 0,
  "citations": null | [
    {"id": "<uuid>", "url": "<source url>", "score": <float 0-1, relevance/similarity>, "title": "<source title>"}
  ],
  "reasoning_summary": null, "chart": null,   // chart populated for chart-style answers, not yet captured -- see below
  "created_at": "..."
}
```
`citations` is only present on `assistant` messages and is the grounding
set Ubi actually drew from (confirmed: for a feed-wide question it returned
15 citations with `score` descending by relevance, each tied to a real
artifact URL already in the feed) -- this is the auditable "what did Ubi
actually look at" trail, worth surfacing to a user who wants to verify an
answer rather than trust the prose alone.

Fetching an individual session's own metadata (not needed for history, but
confirmed as a side-effect call the UI also makes):
```
GET /api/understand/chat/sessions/<session_id>?keycloak_user_id=<email>
```

## Charts -- CONFIRMED on the wire
`chart` is `null` on plain prose/table answers (confirmed across several
questions) and only gets populated when the question explicitly asks for
a chart/visual -- it does NOT appear to be triggered implicitly by
comparative or trend-shaped questions on their own; say "chart"/"graph"/
"show me a chart of..." in the question. Confirmed shape, from asking
"Show me a chart of sentiment trends about renewable energy over the past
2 weeks, broken down by week":
```json
{
  "type": "stackedBar",
  "title": "Renewable Energy Sentiment by Week (%)",
  "config": {
    "xaxis": {"categories": ["Week 1 (Sep 18\u201325)", "Week 2 (Sep 26\u2013Oct 2)"]},
    "yaxis": {"title": {"text": "Sentiment (%)"}},
    "series": [
      {"name": "Positive", "data": [55, 50]},
      {"name": "Negative", "data": [30, 35]},
      {"name": "Neutral", "data": [15, 15]}
    ]
  }
}
```
This is an ApexCharts-style config object (`type`/`xaxis`/`yaxis`/`series`
naming matches the ApexCharts JS library's option schema directly) --
the frontend almost certainly feeds `config` straight into an ApexCharts
component keyed by `type`. The `content` (markdown prose) field is still
populated alongside the chart with a full breakdown -- the chart
supplements the prose, it doesn't replace it. `citations` was also
populated normally (375 sources) on this same message, so chart-requesting
questions still get the full grounding trail. Other `type` values (e.g.
line, pie, bar) are plausible given the ApexCharts pattern but not yet
individually confirmed -- if you need a specific chart type, ask for it by
name in the question (e.g. "as a line chart") and verify `chart.type`
matches.

Response latency for a chart-requesting question was notably longer than a
plain prose question (~40s+ observed vs. ~15-25s) -- budget for that when
polling.

## Artifacts backing the chat
```
GET /api/understand/artifacts/count/<feed_id>   -> {count, feed_id}
POST /api/understand/artifacts/preview
  {"feed_id": <feed_id>, "filter_state": {}, "limit": 1000}
```
See `ubiquity-understand-layer` for the confirmed request shape and the
"Collection `<email>` doesn't exist" 500 you'll get before any artifacts
have actually been ingested (discovering sources is not the same as
ingesting their content -- that's a separate, later step). Ubi's answers
are grounded in these ingested artifacts (confirmed via `citations` above)
-- i.e. "querying the data feed api" maps to this `understand` service
family (`artifacts/*`) plus the raw entities listing in
`ubiquity-entity-review`.

## Custom metrics are queryable in chat
If a user has added custom metrics to this pipeline/feed (see
`ubiquity-metric-generators`), those metrics' computed values are
available to Ubi chat directly -- Ubi can reference and reason over metric
values in its answers, not just the raw article/post content, so it's
worth telling a user their defined metrics are chat-queryable once set up
(e.g. "What's the trend in my [metric name] metric this month?"). This is
also presumably what the `filter_state.metricName` field (see below) is
for -- scoping a whole session to one specific metric.

## filter_state fields -- auto-derived per session, with caveats
Each session's `filter_state` (see schema above) is auto-populated from
the first message's wording when a session is created, but not every
field is reliably inferred the same way -- notes per field:

- `textSearch` ("Text Filter" in the UI): an **exact word/phrase match**
  filter, not semantic/fuzzy -- use it (or expect Ubi to derive it) when
  the user wants artifacts containing a specific literal term, as
  distinct from `topics` (semantic topic matching). Confirmed null on
  every session captured so far -- not yet seen Ubi auto-populate this
  from a question's wording; may need to be set explicitly rather than
  relying on inference, if the UI exposes a direct filter control (not
  yet located in the Understand tab chrome -- check for a filter icon/
  panel near the chat input if a user wants this set manually).
- `entityTypes`: filters by entity type -- confirmed categories include
  distinguishing **individuals vs. institutions** (consistent with the
  entity-type vocabulary used elsewhere in Ubiquity, see
  `ubiquity-entity-review`). Also confirmed null on every session so far
  -- same caveat as `textSearch`, inference from question wording not yet
  observed to populate this one either (only `siteTypes` was confirmed
  auto-derived, from "Twitter" -> `["micro_blog"]`).
- `dateRange`: defaults to the **last 30 days** when not otherwise implied
  by the question (confirmed: a feed-wide question with no date wording
  got `start`/`end` spanning ~30 days back from today; a question that
  said "past 7 days" got a 7-day range instead, so explicit timeframe
  language in the question DOES override the 30-day default). **Caveat:
  longer timelines take longer to process** -- a multi-week/multi-month
  range means Ubi scans more artifacts, so expect proportionally longer
  response latency (already noted above: ~15-25s for a narrow/short-range
  question, 40s+ for a 2-week chart-and-breakdown question) -- warn a user
  asking for a long historical range (e.g. "since the pipeline started")
  that it may take noticeably longer, and don't assume a stall just
  because it's slower than a short-range question.
- `siteTypes`: confirmed auto-derived from platform names in the question
  ("Twitter" -> `["micro_blog"]"), see the worked example above.
- `topics`, `metricName`: not yet observed populated in any captured
  session; `metricName` is presumably how a session scopes to one of the
  pipeline's custom metrics specifically (see metrics note above) rather
  than the whole feed -- not yet confirmed how to trigger this via
  question wording vs. an explicit UI control. **Confirmed:** `metricName`
  staying `null` does NOT prevent metric-aware answers -- asking a
  question that explicitly names an active metric (e.g. "Based on the
  Stance toward Renewable Energy Policy metric...") got a fully
  metric-grounded answer (exact average/min/max/distribution numbers
  pulled from the computed per-article scores) with `filter_state.
  metricName` still `null` on the created session. So Ubi has ambient
  access to all `active: true` metrics on the feed regardless of this
  filter field -- `metricName` is likely only a UI-level scoping/display
  filter (e.g. restricting which metric's chart shows), not a precondition
  for Ubi being able to reason over metric data in chat.

## Practical notes
- Chat responses take a few seconds (observed ~15-25s for a feed-wide
  question over hundreds of sources) -- poll
  `GET .../messages?...` after sending rather than assuming an instant
  reply; the UI itself shows a "Thinking Process" state while waiting.
- Ubi cites real per-artifact URLs with relevance scores, and its answers
  read as genuinely grounded (specific quoted snippets tied to specific
  cited sources) rather than generic LLM filler -- spot-check a citation's
  URL/title against the question when verifying an answer for a user.
- The `keycloak_user_id` query param on every GET is literally your email
  (url-encoded, e.g. `+` -> `%2B`), not a UUID -- don't confuse this with
  the Keycloak `sub` UUID used elsewhere (see `ubiquity-auth`).
